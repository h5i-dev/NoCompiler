# safe/unsafe 型付き RISC-V アセンブリ 設計ノート v0

Nov 23, 2026 · @Syumei

## 要約

型が追う事実は二種類だけにする。「このレジスタの値は整数変数の一次式に等しい」と「この関数はこの番地範囲を使ってよい」。safe な関数では、検査機がこの二つから全メモリアクセスが許された範囲に入ることを確かめる。unsafe な関数は同じ形の署名を契約として持ち、中身は検査しない。

- **このノートで決めること**: 安全性の主張の文面、型の言語、型付け規則、署名の意味。
- **前提にした決定**: unsafe の契約は仮定し、必要な分だけ手で証明する。safe の検査は当面 Rust 製の検査機を信頼し、健全性を Lean で示した検査機は後で別に作る。全正当性を既定にし、止まらない関数だけ partial と明示する。機械モデルの外のコードを呼ぶことは認める。
- **その帰結**: Lean に最初から要るのは「署名の意味」の定義だけになる。これがないと、unsafe 部分の手書き証明が何を示せばよいか決まらない。
- **v0 の範囲**: バッファと長さを扱うコードと、バッファへのポインタを持つ構造体。数が決まっていないポインタを持つ構造（連結リスト、ポインタの配列、木）は safe では書けず、unsafe に回る。
- **確かでないこと**: 規則の健全性は自然言語の証明があるだけで、機械検査していない。表現力が足りるかは実例を書くまで分からない。検査にかかる時間も未計測。

構文はすべて仮のもの。意味が固まってから決める。

検査機が通した safe 関数も、仮定した unsafe 関数も、手で証明した unsafe 関数も、主張する内容は同じ「署名の意味」である。違うのは根拠だけで、それを台帳が記録する。

## 安全性の定理

主張は一つにする。「検査を通った safe 関数は、それが呼ぶ関数の契約がすべて成り立つなら、自分の署名の意味を満たす」。

### 署名の意味

署名 σ の意味 ⟦σ⟧ は、機械意味論の上の命題として Lean で定義する。e5r の `Spec` をそのまま使える形にする。中身は三つ。

1. **入口で仮定すること**: レジスタの値が署名どおり。制約が成り立つ。各能力の範囲が妥当（先頭 ≥ 0、長さ ≥ 0、先頭 + 長さ ≤ 2^64）。書込み可能な範囲は、ほかのどの範囲ともスタックとも重ならない。
2. **実行中に守ること**: 読むのは渡された範囲と自分のスタックだけ。書くのは書込み可能な範囲と自分のスタックだけ。
3. **出口で保証すること**: `ra` の指す先へ戻る。`sp` と callee-saved は入口の値。結果レジスタは署名どおり。貸した能力はそのまま返る。新しく渡す能力と返すトークンの範囲は、take で受け取った範囲と借りたトークンの範囲の内側にあり、互いに重ならない。exit で終了した場合は、この保証の代わりに終了したことだけを言う。

2 は e5r では「行き詰まらない」と同じ意味になる。e5r の `Step` は権限外のアクセス、整列していないアクセス、復号できない命令に次の状態を与えないからである。

3 の最後の条件（出る範囲 ⊆ 入った範囲）は、呼出し側が持ち続けているほかの範囲と、返ってきた範囲が重ならないことを保証する。`malloc` の返す領域がほかと重ならない理由もこれで説明する（「unsafe と契約」の節）。

### 強さは二段

| 段 | 内容 | Lean での形 |
| --- | --- | --- |
| 部分 | 止まるまで 2 を守り、止まるなら 3 が成り立つ | 新しい判定が要る。現行の `Exec` は必ず止まることまで含む |
| 全 | 部分に加えて、必ず止まる | 現行の `VerifiedImg` そのもの |

既定は全にする（11/23 決定）。止まらない関数だけ partial と明示し、その関数には部分の意味を与える。partial な関数を呼べるのは partial な関数だけになる。部分の判定を Lean に足すのは、partial な関数が実際に要るようになってからでよい。

### 主張しないこと

- 機能の正しさ。従来どおり手書きの証明で示す。
- メモリの中身。初期化前の領域を読んでも安全で、任意のバイト列が読めるだけ。
- 解放漏れ。能力は捨ててよい。
- unsafe の契約が正しいこと。定理はそれを仮定に取る。
- 整数のあふれがないこと。算術は 2^64 を法とした計算として定義どおりに扱う。

### 「メモリ安全」の定義についての注意

機械にはオブジェクトがないので、ここでの定義は「すべてのアクセスは、その時点で保持している能力の範囲に入る」になる。能力の出どころは四つだけ: 呼出し元から受け取る、自分のフレーム、unsafe 関数の出口、静的データ。

解放後の使用は、`free` が能力を消費し、能力がなければアクセスが型検査を通らないことで防ぐ。これは `free` の契約が正しいことに依存する。

### 手書きの機能証明に対して型が与えるもの

過大に見積もらないために書いておく。v0 の型が機能証明から取り除くのは次の三つで、値についてのループ不変条件は残る。

- 境界、整列、権限の副条件。
- 呼出しをまたいで変わらないメモリの範囲。署名から読める。
- 書込み可能な二つの範囲が重ならないという事実。

以前の実測で、一つ目は元から安い義務だった。効くとすれば二つ目と三つ目で、どの程度かは分からない。

## 型の言語 v0

値の型は一種類、能力は二種類にする。ポインタ専用の型は作らない。

### 添字と制約

- **添字変数** `x`, `n`, `ρ` などは数学の整数を動く。レジスタではなく論理変数なので、値は変わらない。
- **添字式** `e` は一次式 `c0 + c1·x1 + …`。
- **制約** `ψ` は `e1 ≤ e2`、`e1 = e2`、`c ∣ e`（定数 c が e を割り切る）と、その ∧ ∨ ¬。量化子のないプレスバーガー算術で、成否は決定できる。

### 値の型

| 型 | 意味 |
| --- | --- |
| `int(e)` | レジスタの 64 ビット語が、e を 2^64 で割った余りに等しい |
| `int` | ある新しい変数 x について `int(x)`。何も分かっていない語 |

ポインタは「番地を表す添字変数 ρ を含む一次式」で表す。例: `int(ρ + 8k)`。入口の `ra` や callee-saved も `int(x)` と置くだけで、出口で同じ `int(x)` であることを求めれば保存が表せる。

2^64 を法として定義するのは、`add`、`sub`、定数シフト、定数倍が副条件なしで正確に型付けできるからである。範囲の事実が要るのは、順序が意味を持つ比較とメモリアクセスだけになる。

略記: `u64(e)` は `int(e)` かつ `0 ≤ e < 2^64`。`i64(e)` は `int(e)` かつ `−2^63 ≤ e < 2^63`。

### 能力

| 能力 | 意味 |
| --- | --- |
| `e ↦ bytes[n] rw` | 番地 e から n バイトを読み書きしてよい |
| `e ↦ bytes[n] ro` | 同じ範囲を読んでよい |
| `e ↦ bytes[n] rw heap` | 割当て単位そのもの。`free` が受け取れるのはこの印が付いた全体だけ |
| `T`（不透明トークン） | unsafe モジュールが宣言する名前付きの資源。例: `Heap`。safe コードは持ち回るだけで、その範囲には触れられない |
| e ↦ bytes\[n\] rw {k: int(e′), …} | フィールド付き。先頭から k バイト目の 8 バイトの語が int(e′) を満たす。ro の能力にも付けられる |

能力は複製できない。捨てるのはよい。メモリの中身については、能力に付けた**フィールド**の分だけ事実を持つ。フィールド `k: int(e)` は「能力の先頭から k バイト目にある 8 バイトの語が `int(e)` を満たす」という意味で、それ以外の場所から読み出した値は `int` になる。

フィールドは中身についての事実であって、権限ではない。フィールドが指す先を使うには、その先の能力を別に持っている必要がある。

この二つの選択から次が出る。

1. **ポインタは権限を持たない。** 権限は能力にある。範囲外を指すポインタを作っても、メモリに保存しても、返しても安全で、検査は参照するときだけ行う。
2. **lifetime に当たる仕組みが要らない。** 貸し借りは呼出しの間だけで、権限はメモリにも戻り値のポインタにも入らない。`memchr` のように借りた範囲の内側を指すポインタを返す関数は、戻り値を `int(ρ + k)` と書くだけで済む。
3. **別名の解析が要らない。** アクセスは「どの能力の何バイト目か」を算術で決めるので、同じ場所を指す二つのポインタは同じフィールドに行き着く。`rw` の能力はほかの能力と重ならないから、ストアが壊し得る事実は、書いた能力自身のフィールドだけである。
4. **数が決まっているポインタは検査なしで使える。** 構造体にバッファのポインタと長さを置き、署名に構造体の能力とバッファの能力を並べて書く。
5. **代償として、能力の数は署名に書ける数に限られる。** ポインタの配列、連結リスト、木は safe では書けない。

```
fn parse [ρ, β, n]
  in     a0: int(ρ)
  borrow ρ ↦ bytes[16] ro {0: int(β), 8: int(n)}
  borrow β ↦ bytes[n] ro
  where  8 ∣ ρ
  out    a0: int
```

この関数の中で `ld a1, 0(a0)` は `a1: int(β)` を、`ld a2, 8(a0)` は `a2: int(n)` を与える。以降の β 経由のアクセスは、長さ n に対して静的に検査される。

### 状態の型

プログラム点ごとに五つ組 (Δ; Ψ; Γ; Φ; C) を持つ。

| 成分 | 内容 |
| --- | --- |
| Δ | 添字変数 |
| Ψ | 制約 |
| Γ | レジスタから型へ |
| Φ | フレームのスロットから型へ。R6 の「番地を取られないスロット」が対象 |
| C | 保持している能力 |

意味: ある付値 ι : Δ → ℤ があって、Γ と Φ が実際の値と一致し、Ψ が真で、C の各能力の範囲が妥当で互いに重ならず（`ro` どうしは重なってよい）、スロット領域とも重ならず、各トークンの不変条件が成り立つ。

能力を持っていること自体が事実を生む。`e ↦ bytes[n]` を持っている間、`0 ≤ e`、`0 ≤ n`、`e + n ≤ 2^64` を Ψ に加えてよい。

### 署名

```
fn sum [ρ, n]
  in     a0: int(ρ), a1: int(n)
  borrow ρ ↦ bytes[8n] ro
  where  8 ∣ ρ
  out    a0: int
  stack  0
```

| 句 | 意味 |
| --- | --- |
| `[…]` | 入口で全称の添字変数。`out` で新しく出る変数は存在量化 |
| `in` / `out` | 入口と出口のレジスタの型。`out` に書かない caller-saved は `int` |
| `borrow` | 呼出しの間だけ借り、同じものを返す |
| `take` | 受け取って返さない |
| `give` | 出口で新しく渡す。`p ≠ 0 ⇒ …` のように条件を付けられる |
| `where` | 制約。入口側にも出口側にも書ける |
| `stack` | 使うスタックのバイト数 |

署名に `partial` と書いた関数は、止まることを保証しない。書かない関数は、必ず止まることまで検査する。

## 型付け規則

規則は「命令の前の状態の型から、後の状態の型を作る」形で、検査が要るのはメモリアクセス、ループの入口、呼出し、戻りの四か所だけである。制御とスタックの形は現行の R1–R6 をそのまま使う。

記法: `e_r` はレジスタ r の現在の添字式。`u(e)` は e の符号なしの代表元で、新しい変数 x, k を取り `e = x + 2^64·k`、`0 ≤ x < 2^64` と置いたときの x。`s(e)` は符号付きの代表元。Ψ から `0 ≤ e < 2^64` が出るなら `u(e) = e` で、新しい変数は要らない。`x0` は常に `int(0)`。

### 算術

| 命令 | rd の型 | Ψ に加わる事実 |
| --- | --- | --- |
| `addi rd, rs, c` | `int(e_rs + c)` | なし |
| `add` / `sub` | `int(e1 ± e2)` | なし |
| `slli rd, rs, c` | `int(2^c · e_rs)` | なし |
| `sh1add` / `sh2add` / `sh3add` | `int(2^N · e1 + e2)` | なし |
| `mul`（片方が定数 `int(c)`） | `int(c · e)` | なし |
| `andi rd, rs, c`（c ≥ 0） | `int(x)` | `0 ≤ x ≤ c`。c = 2^k − 1 なら `e_rs = x + 2^k·j` も |
| `srli rd, rs, c` | `int(x)` | `u(e_rs) = 2^c·x + r`、`0 ≤ r < 2^c` |
| `minu rd, rs1, rs2` | `int(x)` | `x ≤ u(e1)`、`x ≤ u(e2)`、`0 ≤ x` |
| `remu rd, rs1, rs2` | `int(x)` | Ψ から `u(e2) > 0` が出るとき `0 ≤ x < u(e2)` |
| `addw` など 32 ビット演算 | `int(x)` | `e1 + e2 = x + 2^32·j`、`−2^31 ≤ x < 2^31` |
| 表にない命令 | `int(x)` | `0 ≤ x < 2^64` だけ |

どのレジスタもいつでも `int` に弱めてよく、Ψ の事実はいつでも捨ててよい。だから表が粗くても健全性は損なわれず、損なわれるのは検査を通せるプログラムの範囲である。この表は暫定で、実例を書きながら足す。

### メモリ

幅 w バイトのロード `l* rd, c(rs)` は、番地 `a = e_rs + c` について、C の中のある能力 `b ↦ bytes[n]` が次を満たすときに通る。

```
Ψ ⊢  b ≤ a  ∧  a + w ≤ b + n  ∧  w ∣ a
```

- 結果は `int(x)`。`lbu` なら `0 ≤ x < 256`、`lb` なら `−128 ≤ x < 128` のように、幅と符号から範囲が付く。
- ストア `s* rs2, c(rs1)` は同じ条件に加えて、能力が `rw` であることを求める。型の状態は変わらない。
- 能力があるので `0 ≤ b`、`b + n ≤ 2^64` が使え、a は折り返さずに実際の番地と一致する。
- スロットへの `sd rs, k(sp)` は Φ\[k\] に Γ(rs) を写し、`ld rd, k(sp)` は Γ(rd) に Φ\[k\] を写す。レジスタの退避で型が失われないのはこの規則による。

**フィールドの規則**

- 8 バイトのロードで、Ψ から `a = b + k` が出て、当てた能力にフィールド `k: int(e)` があれば、結果は `int(e)` になる。
- `rw` の能力への 8 バイトのストアで、Ψ から定数 k について `a = b + k` が出れば、フィールド k を、書いた値の型に置き換える。
- それ以外のストア（番地が定数の位置に決まらない、または 8 バイト未満）は、その能力のフィールドのうち、書いた範囲と重ならないと示せないものを捨てる。フィールドの途中に 1 バイト書けば、そのフィールドは消える。
- 呼出しで `rw` として貸した範囲と重なり得るフィールドは、呼出しの後に捨てる。相手の署名が出口のフィールドを書いていれば、それに置き換える。`ro` で貸したときは残る。

条件付きの能力 `ψ ⇒ c` は、Ψ から ψ が出るプログラム点で c として使える。`malloc` の結果を null 検査した後がこれに当たる。

### 分岐

| 命令 | 成立側に加わる事実 | 不成立側に加わる事実 |
| --- | --- | --- |
| `bltu rs1, rs2` | `u(e1) < u(e2)` | `u(e1) ≥ u(e2)` |
| `blt rs1, rs2` | `s(e1) < s(e2)` | `s(e1) ≥ s(e2)` |
| `beq rs1, rs2` | `2^64 ∣ e1 − e2` | `¬(2^64 ∣ e1 − e2)` |

`bgeu`、`bge`、`bne` は左右を入れ替えたもの。明示的な境界検査や null 検査は、この規則で Ψ に事実が入ることで効く。

### 合流とループ

- **ループの形（2026-11-23 P1 adopted (user)）。** 戻りの辺は u → h で h が u を支配する辺、h は注釈の付いたループ入口とする。戻りの辺を除いた制御フローは非巡回でなければならず、ループは h の自然ループである。検査は、どの自然ループも連続する点の順序 τ（記録が与える）で行い、番地の順は使わない。理由: clang のブロック配置では、帰約可能な制御フローでも番地の順にループが区間にならないことが多く（musl の試行で 29 ファイル中 8）、番地で区間を求めると、正しくコンパイルされた関数を構造だけで落としてしまう。停止の証明（定理 C）は番地を τ に読み替えるだけで変わらない。ループの入口でない点に書いた `inv` は合流の注釈として働く。
- **ループの入口には注釈が要る。** 形は `inv [m, …] r: int(e), … where ψ decreases e`。添字変数は値が変わらないので、ループの前に成り立っていた Ψ はそのまま残る。注釈に書くのは、ループ内で書き換わるレジスタの新しい型だけで済む。書き換わるのに注釈にないレジスタは `int`。
- **入口の辺と戻りの辺で注釈を証明する。** `[m, …]` の具体化は、注釈が `r: int(m)` と裸で書いているレジスタの現在の式から取る。取れない変数は明示的に与える。そのうえで、残りのレジスタの式が法 2^64 で一致することと ψ を示す。
- **`decreases e`** は、戻りの辺で `0 ≤ e` かつ次の周の e が真に小さいことを示す。partial と明示していない関数のループでは必須。
- \*\*前向きの合流（ブロックの終端）\*\*の v0 案: 全ての入辺で式が一致するレジスタはそのまま、一致しないものは `int`。分岐の中で加わった事実は捨てる。足りないときはループと同じ形の注釈を置く。分岐条件を付けた選言で正確に合流する別案は採らない（決定 2）。
- 合流後の能力の集合 C は、全ての入辺に共通する能力だけになる。ループの戻りの辺では、入口で持っていた能力をすべて持っていることを求める。

### 呼出し

`jal ra, f` は、f の署名に対して次の順で検査する。

1. **具体化を決める。** 署名の `[…]` の各変数を、`in` が裸で書いているレジスタの現在の式から取る。取れなければ能力の照合から、それでもなければ注釈から取る。
2. **引数と制約を示す。** `in` の各レジスタの式が法 2^64 で一致し、`where` が Ψ から出る。
3. **能力を照合する。** `borrow b ↦ bytes[n]` には、保持中の能力 `b0 ↦ bytes[n0]` で `b0 ≤ b ∧ b + n ≤ b0 + n0` を満たすものを当てる。一部分だけ貸すのはこれで表せる。`rw` の貸出しは、同じ呼出しのほかのどの貸出しとも範囲が重ならないことを示す。`ro` どうしは重なってよい。`take` は範囲と印が完全に一致する能力を当てて、C から取り除く。
4. **スタックを確かめる。** 自分のフレームの大きさ + f の `stack` ≤ 自分の `stack`。
5. **呼出し後の状態を作る。** `sp`、callee-saved、スロット Φ はそのまま。`out` のレジスタは署名どおりで、新しい変数は新しく取る。それ以外の caller-saved と `ra` は `int`。貸した能力はそのまま残り、`give` の能力が加わり、出口側の `where` が Ψ に加わる。

呼出しの検査には、証明の過程で足した条件が四つある。

- 貸す範囲の長さについて `0 ≤ n` も示す。これがないと、負の長さで範囲の条件がすり抜ける。
- `take` に当てた能力は、同じ呼出しのほかの句には当てられない。
- 相手の署名がフィールドを書いていれば、当てた能力の同じ番地にフィールドがあり、式が法 2^64 で一致することを示す。変数の具体化はフィールドからも取れる。
- `partial` でない関数からは、`partial` な関数を呼べない。

スロットがそのまま残ると言えるのは、呼ばれた側が触れるのは渡された能力の範囲と自分の `sp` より下だけで、どの能力もスロット領域と重ならないからである。末尾呼出しは「呼出しの検査 + 戻りの検査」として扱う。

### 戻り

`jalr zero, 0(ra)` は次を示す。

- `ra`、`sp`、`s0`–`s11` の式が入口の変数と法 2^64 で一致する。
- `out` のレジスタの型と出口側の `where` が成り立つ。存在変数の具体化はループと同じ要領で取る。
- `borrow` で受け取った能力を、同じ範囲のまま持っている。
- `give` する能力を持っている。一つの能力は、返す・渡すのどれか一つにしか当てられない。`give` できるのは `rw` の能力とトークンだけである。

### フレームの能力

R6 が「番地を取る範囲」と宣言したフレーム内の範囲は、`sp` を下げる命令の直後に `rw` の能力になる。`addi rd, sp, k` は算術の規則どおり `int(e_sp + k)` を与えるだけで、特別な規則は要らない。`heap` の印がないので `free` には渡せない。

`sp` を戻す命令は、そのフレームの能力をすべて、宣言どおりの範囲で持っていることを確かめ、そこで能力とスロット Φ を捨てる。戻りの時点で確かめるのでは遅い。`sp` を戻した後に別の関数を呼ぶと、その関数のスタックが、まだ残っている能力の範囲と重なるからである。

### 静的データ

記号 sym を指す `auipc` と `addi` の対は、`rd: int(ℓ_sym)` を与える。`ℓ_sym` はその記号の番地を表す添字変数である。読取り専用のデータの能力は、すべての関数が暗黙に `ro` で持つ。書込み可能なデータの能力は `_start` の署名に現れ、そこから署名を通して受け渡す。

### システムコール

`ecall` は `a7` が定数 `int(c)` で、c が environment.md の四つ（63, 64, 93, 94）のどれかであることを求め、番号ごとの署名で呼出しと同じように検査する。ただし `a0` 以外のレジスタは保存される。

```
sys write [b, n]   in a1: int(b), a2: int(n)   borrow b ↦ bytes[n] ro
                   out a0: int(r) where −4095 ≤ r ≤ n, r ≤ 0x7ffff000
sys read  [b, n]   in a1: int(b), a2: int(n)   borrow b ↦ bytes[n] rw
                   out a0: int(r) where −4095 ≤ r ≤ n, r ≤ 0x7ffff000
sys exit           戻らない
```

`write` と `read` は `0 ≤ n < 2^64` を入口の制約に持つ。この署名は `Env.lean` の関係から導けるはずだが、確かめていない。

`write` と `read` の結果に `r ≤ 0x7ffff000` を付けるのは、これがないと r が符号付きの範囲に入ることが言えず、`blt a0, zero` のエラー検査から `r ≥ 0` が出ないからである。この種の見落としが、誤りの入りやすい箇所の実例になる。

## 例

リポジトリの `sum`（clang -O2 の出力そのまま）は、注釈 1 個、追加命令 0 個で検査を通るはずである。下は規則を手で当てた結果で、検査機で確かめたものではない。

### sum

```
fn sum [ρ, n]
  in     a0: int(ρ), a1: int(n)
  borrow ρ ↦ bytes[8n] ro
  where  8 ∣ ρ
  out    a0: int
  stack  0

sum:
    addi a2, zero, 0
    beq  a1, zero, done
loop:                    # inv [m] a0: int(ρ + 8n − 8m), a1: int(m), a2: int
                         #     where 1 ≤ m ≤ n   decreases m
    ld   a3, 0(a0)
    add  a2, a3, a2
    addi a1, a1, -1
    addi a0, a0, 8
    bne  a1, zero, loop
done:
    addi a0, a2, 0
    jalr zero, 0(ra)
```

| 場所 | 示すこと | 使う事実 |
| --- | --- | --- |
| 入口 | なし | 能力から `0 ≤ 8n`、`ρ + 8n ≤ 2^64`。よって `0 ≤ n < 2^64` |
| `beq` の不成立側 | `n ≥ 1` | `¬(2^64 ∣ n)` と `0 ≤ n < 2^64` |
| `loop` への入口の辺 | m := n で注釈が成り立つ | `ρ = ρ + 8n − 8n`、`1 ≤ n ≤ n` |
| `ld a3, 0(a0)` | `ρ ≤ ρ + 8n − 8m`、`ρ + 8n − 8m + 8 ≤ ρ + 8n`、`8 ∣ ρ + 8n − 8m` | `m ≤ n`、`1 ≤ m`、`8 ∣ ρ` |
| `bne` の成立側 | `m − 1 ≥ 1` | `¬(2^64 ∣ m − 1)` と `0 ≤ m − 1 < 2^64` |
| `loop` への戻りの辺 | m := m − 1 で注釈が成り立ち、m が減る | `ρ + 8n − 8m + 8 = ρ + 8n − 8(m − 1)`、`1 ≤ m − 1 ≤ n`、`0 ≤ m` |
| `done`（合流） | なし | `a0`、`a1`、`a2` は入辺で式が違うので `int` |
| `jalr` | `ra`、`sp`、`s0`–`s11` が入口のまま。`a0: int`。借りた能力を持っている | どれも書き換えていない |

制約はすべて一次で、新しい変数を取る必要があったのはループの m だけである。

### スタック上のバッファと呼出し

フレーム内の 64 バイトに `read` で読み込み、読めた長さだけを別の safe 関数に貸す。長さ r は実行時の値だが、システムコールの署名が上限を与えるので、追加の比較はエラー検査の 1 個だけで済む。

```
fn sum_bytes [ρ, n]
  in a0: int(ρ), a1: int(n)   borrow ρ ↦ bytes[n] ro   out a0: int   stack 0

fn read_sum []
  out a0: int   stack 80

read_sum:
    addi sp, sp, -80     # スロット 72 = ra。[0, 64) は番地を取る範囲
    sd   ra, 72(sp)      # Φ[72] = int(x_ra)
    addi a1, sp, 0       # a1: int(φ)。フレームの能力 φ ↦ bytes[64] rw
    addi a0, zero, 0
    addi a2, zero, 64
    addi a7, zero, 63
    ecall                # read: b := φ, n := 64。a0: int(r), −4095 ≤ r ≤ 64
    blt  a0, zero, fail  # 不成立側: r ≥ 0
    addi a1, a0, 0       # a1: int(r)
    addi a0, sp, 0       # a0: int(φ)
    jal  ra, sum_bytes   # ρ := φ, n := r。φ ≤ φ ∧ φ + r ≤ φ + 64
out:
    ld   ra, 72(sp)      # ra: int(x_ra)
    addi sp, sp, 80
    jalr zero, 0(ra)
fail:
    addi a0, zero, 0
    jal  zero, out
```

`sum_bytes` が返った後も Φ\[72\] が `int(x_ra)` のままだと言えるのは、貸したのが `[φ, φ + r)` だけで、スロットはどの能力にも入っていないからである。

### malloc と free の契約

```
unsafe fn malloc [n]
  in     a0: int(n)
  borrow Heap
  where  0 ≤ n < 2^64
  out    a0: int(p)
  give   p ≠ 0 ⇒ p ↦ bytes[n] rw heap
  where  0 ≤ p < 2^64, 16 ∣ p

unsafe fn free [p, n]
  in     a0: int(p)
  take   p ↦ bytes[n] rw heap
  borrow Heap
```

```
    jal  ra, malloc      # a0: int(p)。能力はまだ条件付き
    beq  a0, zero, oom   # 不成立側: p ≠ 0。能力 p ↦ bytes[n] rw heap が使える
    addi s1, a0, 0
    sd   zero, 0(s1)     # Ψ から 8 ≤ n が出れば通る
    addi a0, s1, 0
    jal  ra, free        # 能力を消費する。n は能力の照合から決まる
    ld   a1, 0(s1)       # 検査で落ちる。s1 は int(p) のままだが、当てる能力がない
```

解放後の使用と二重解放は、どちらも「当てる能力がない」で落ちる。environment.md には `mmap` も `brk` もないので、`Heap` は静的な領域から作ることになる（次節）。

## unsafe と契約

unsafe 関数は safe 関数と同じ形の署名を持ち、中身は検査されない。署名が成り立つ根拠は四通りあり、関数ごとに台帳に記録する。

| 状態 | 根拠 | Lean から見た扱い |
| --- | --- | --- |
| 証明済み | ⟦σ⟧ に対する手書きの証明（現行の `VerifiedImg`） | 定理 |
| 検査済み | Rust の検査機が通した safe 関数 | 仮定 |
| 仮定 | 誰も確かめていない unsafe 関数 | 仮定 |
| 外部 | 機械モデルの外のコード。確かめる手段がない | 環境モデルの一部として置く。証明の対象にならない |

当面、検査済みと仮定は Lean の中では同じ「仮定」で、違いは台帳の上にしかない。Lean の検査機ができた時点で、検査済みが定理に移る。

手書きの証明は、呼ぶ関数の ⟦σ⟧ を仮説に取る形で書く。そうしておけば、相手の状態が後で変わっても証明は変わらない。

### 契約を仮定するときに、暗に仮定していること

署名に書いた型だけでなく、次の四つも ⟦σ⟧ に含まれる。unsafe を書く側が守る義務である。

1. 触れるのは、受け取った能力の範囲と自分のスタックだけ。
2. `give` する範囲は、受け取った範囲の内側。
3. `ra` の指す先へ戻り、`sp` と callee-saved を復元する。
4. トークンの不変条件は、そのトークンの範囲のメモリだけで決まる。ほかの場所への書込みで壊れない。

### 不透明トークン

unsafe モジュールが関数をまたいで内部状態を持つときに使う。ヒープの例:

```
unsafe fn heap_init [b, n]
  in    a0: int(b), a1: int(n)
  take  b ↦ bytes[n] rw
  give  Heap
```

- トークンの意味は「範囲」と「その範囲のメモリについての不変条件」の組で、unsafe モジュールの作者が Lean で与える。範囲は論理上の値で、`malloc` のたびに縮み、`free` で戻る。
- `malloc` の返すブロックが呼出し側のほかの能力と重ならないのは、ブロックが `Heap` の範囲から切り出され、`Heap` の範囲がもともとほかの能力と重なっていなかったからである。「出る範囲 ⊆ 入った範囲」の条件がここで効く。
- safe コードは `Heap` を持ち回るだけで、その範囲に対するバイト列の能力を持たない。だからアロケータの内部を壊せない。
- ヒープを使う関数は署名に `borrow Heap` と書く。全関数に暗黙に通すことはしない（決定 7）。

### 機械モデルの外にあるコード

要件「既存の RISC-V アセンブリは unsafe 扱い」には、区別が一つ要る。

- **プロファイル内の命令だけで書かれた unsafe コード**: 契約は機械意味論の上の命題で、仮定も証明もできる。
- **プロファイル外の命令を含むコード**（圧縮命令、浮動小数点、計算ジャンプ、四つ以外のシステムコール）: e5r の機械はそれを実行できず、次の状態がない。その関数について ⟦σ⟧ を Lean で仮定すると偏の仮定になり、そこから何でも証明できてしまう。

後者は `ecall` と同じ扱いにするしかない。「この番地を呼ぶと契約どおりの状態遷移が起きる」を環境モデルの拡張として置く。証明の対象にはならず、信頼対象がその分増える。コンパイラの既定の出力は圧縮命令を含むので、プロファイルの命令集合で組み直さない限り後者になる。これを呼ぶことは認める（11/23 決定）。台帳では「外部」という別の状態にして、仮定と区別する。

この決定から作業が一つ出る。外部の関数を呼ぶ一歩を `Step` にどう入れるかで、信頼対象の意味論そのものを変える変更になる。入れ方は ecall と同じ形にする（決定 9）。

### unsafe の単位

v0 では関数を単位にする。safe 関数の中の一区間だけを unsafe にする形（区間の入口と出口に状態の型を書く）は意味の上では同じだが、後回しにする（決定 3）。

## 健全性の取り方と信頼対象

当面は「紙の上の規則と Rust の検査機」を信頼し、Lean で健全性を示した検査機は後で別に作る。型の言語がまだ動く段階で証明を先に書くと、規則を変えるたびに証明が壊れるので、この順序は妥当だと考える。

代わりに、それまでの間「safe」の意味は「Rust の検査機が通した」であり、規則そのものの誤りも、検査機の実装の誤りも、そのまま安全性の穴になる。

### 信頼するもの

| 対象 | 当面 | Lean の検査機ができた後 |
| --- | --- | --- |
| e5r の機械意味論と環境モデル | 信頼 | 信頼 |
| 署名の意味 ⟦σ⟧ の定義 | 信頼（読んで確かめる） | 信頼（読んで確かめる） |
| 型付け規則 | 信頼（自然言語の証明のみ） | 証明済み |
| 検査機の実装（Rust） | 信頼 | 信頼しない。速い下見として残る |
| 一次算術のソルバ | 信頼 | 信頼しない。Lean が結果を確かめる |
| 仮定した契約 | 信頼 | 信頼 |
| 外部コードの契約 | 信頼 | 信頼 |

### 今から守っておくこと

後で Lean の検査機を安く作れるようにするための、設計上の約束を三つ提案する。

1. **⟦σ⟧ は最初から Lean で定義する。** 手書き証明の目標であり、検査機が何を保証したことになるかの定義でもある。
2. **規則は一つずつ、機械意味論の上の補題として書ける形に保つ。** 「前の状態の型と検査条件が成り立てば、一歩進めた後の状態の型が成り立つ」。関数全体を見ないと正しさを言えない規則は入れない。
3. **Rust の検査機は判断の記録を出力する。** 各プログラム点の状態の型、変数の具体化、ソルバへの問い合わせ。Lean 側は記録を確かめるだけで済み、探索を作り直さなくてよい。

### 健全性の証明

規則の健全性を自然言語で証明した。本文は別タブ 健全性の証明 にある。示したのは、前提（e5r の機械の性質、プロファイルの構造検査、呼ぶ関数の契約）のもとで、検査を通った関数が署名の意味を満たすことである。機械検査はしていない。

証明の途中で規則の誤りが四つ見つかり、このタブの規則を直した。

- **フレームの能力を確かめる時点。** 戻りではなく、`sp` を戻す命令で確かめて捨てる。
- **`give` の範囲。** 「受け取った範囲の内側」では足りない。借りたバイト列の範囲から `give` すると、貸し手が持ち続けている能力と重なる。`take` で受け取った範囲と借りたトークンの範囲の内側、と直した。
- **貸す長さが負でないことの検査。** 抜けていた。
- **能力の当て方が一対一であること。** 一つの能力を「返す義務」と「渡す義務」の両方に当てられないことが、書かれていなかった。

証明の途中で、e5r の権限の判定との食い違いも一つ見つかった。e5r は「アクセスが領域の一つに収まる」ことを求めるが、`give` で返ってくる能力は、受け取る関数の権限の二つの領域にまたがり得る。権限の判定を「アクセスする全バイトが許されている」に変えることに決めた（11/23、決定 10）。証明は変更後の判定を前提にしている。

この決定で e5r 側に残る作業は三つある。`Step.lean` の `canRead` と `canWrite` の定義を変えること、既存の証明を新しい定義へ移すこと、`trust.md` を更新することである。どれもまだ行っていない。

### 誤りが入りやすいと見ている箇所

- 比較と 2^64 の折返し。代表元の取り方を一か所間違えると境界検査が無意味になる。
- 32 ビット演算の符号拡張。
- `ro` の貸出しが重なるときの呼出し規則。
- 合流点で残す事実と捨てる事実の判断。
- フレームの能力とスロットの境界。R6 のメタデータをそのまま信じている。

### 証明なしでできる点検

検査を通った関数を、権限を強制する実行器の上で、入口の条件を満たす乱数入力について走らせる。行き詰まれば規則か検査機の誤りである。穴がないことは示せないが、ある穴を見つけることはできる。リポジトリには `crates/nocompiler-api/src/emulate.rs` があるが、権限を強制するかどうかは確かめていない。

## 速度

長さから安全性が出るコードは、検査のないコードと同じ命令列で書ける。メモリの中身から安全性が出るコードは、実行時の比較が要るか、unsafe に回る。測定はしていないので、以下は規則から言える予想である。

| 分類 | 例 | 実行時の追加 |
| --- | --- | --- |
| 追加なし | ポインタを進めるループ、カウントダウン、ワード単位のコピーと端数処理、`minu` による長さの切詰め、`remu` で作る添字 | 0 |
| 比較 1 個 | メモリから読んだ値を添字や長さに使う。表引き、長さ付きフィールドのパーサ | 使うたびに `bgeu` 1 個 |
| safe では書けない | 長さなしで終端まで走査する `strlen`、末尾を越えて読むワード単位の走査、数が決まっていないポインタをたどる構造（連結リスト、木）、整列していないアクセス | unsafe に回す |

- **比較 1 個の分類は、正しいプログラムが元々持っている検査と重なることが多い。** パーサの長さ検査がそうである。重ならないのは、データ構造の不変条件で範囲内と分かっている添字で、たとえば自分で埋めたハッシュ表の中の添字がこれに当たる。ここは safe Rust の `v[i]` と同じ損をする。
- **unsafe が関数単位なので、小さな unsafe 操作にも呼出し 1 回の費用がかかる。** ブロック単位の unsafe を後で足す動機はここにある。
- **e5r の機械は整列していないアクセスに次の状態を与えない。** そのため整列の事実（`8 ∣ ρ` など）を署名に書くか、`andi` と分岐で調べる必要がある。

要件「safe だけでもそれなりに高速」に対する現時点の答えは二つに分かれる。バッファ処理については満たせると予想する。バッファへのポインタを持つ構造体も、フィールドの型により追加の検査なしで扱える。連結リストや木については、v0 では safe で書けないので答えがない。添字で表せば書けるが、たどるたびに比較が 1 個加わる。

## v0 に入れないものと、足す順

v0 に入れるのは、数が決まっているポインタ（構造体のフィールド）までである。数が決まっていないポインタ（配列、連結リスト、木）は外す。これを入れるには再帰的な型か量化された能力が要り、v0 の単純さはそこで失われる。

| 入れないもの | 理由 | 足すときに要るもの |
| --- | --- | --- |
| 数が決まっていないポインタ（ポインタの配列、連結リスト、木） | 要素の数だけ能力が要り、署名に書ける数を越える | 再帰的な型か量化された能力と、それを畳む・開くための注釈 |
| 再帰的なデータ型 | 上に依存する | 再帰型 |
| 所有している能力の分割と結合 | 貸出しでの部分範囲はもう表せるので、急がない | 命令を伴わない注釈 `split` / `join` |
| ブロック単位の unsafe | 関数単位で足りるかを先に見る | 区間の入口と出口の状態の型 |
| 再帰 | `stack` が定数だと深さを抑えられない | `stack` を添字式にする（決定 8 で見送り） |
| 関数ポインタ | プロファイルが計算ジャンプを禁じている | プロファイルの変更から |
| 並行性、浮動小数点 | 機械モデルにない | 機械モデルの拡張から |

足す順は実例で決めるのがよい。安いのは能力の分割とブロック単位の unsafe で、大きいのは数が決まっていないポインタである。後者が設計上の次の山になる。

## 先行研究との関係

この設計の部品はどれも既知で、新しいのは組合せと用途だけである。本文を読んだのは LTAL だけで、ほかは要旨の範囲で確かめた。

| 研究 | やったこと | この設計との関係 |
| --- | --- | --- |
| [Proof-Carrying Code](https://www.usenix.org/conference/osdi-96/safe-kernel-extensions-without-run-time-checking)（Necula, Lee, OSDI 1996） | 手で調整した DEC Alpha アセンブリのパケットフィルタに安全性の証明を付け、実行時検査なしで実行させた | 「手書きアセンブリに注釈を付けて安全性を機械的に確かめる」の直接の先例。「判断の記録を出力して後で確かめる」もこの考え方 |
| [DTAL](https://personal.utdallas.edu/~kxh060100/Papers/xi2001dtal.pdf)（Xi, Harper, ICFP 2001） | アセンブリの型に制限付きの依存型を入れ、配列の境界検査を省く最適化を型で正当化した | `int(e)` と一次制約は同じ考え |
| [Alias Types](https://link.springer.com/doi/10.1007/3-540-46425-5_24)（Smith, Walker, Morrisett, ESOP 2000） | 関数が期待するストアの形を別名制約として書き、ポインタの流れを追う | 番地を変数で表し、権限をポインタから切り離す点が同じ。v0 は場所ごとの型を持たず、バイト列だけを扱う |
| [LTAL](https://ecommons.cornell.edu/entities/publication/01389e90-dc2c-4760-b099-27faf61745e8)（Cheney, Morrisett, 2003） | 線形型だけでアセンブリのメモリ管理を型付けし、`malloc` と `free` も型付きのコードとして書いた | メモリの中のポインタを足すときの手本。v0 は共有を貸出しで扱う点が違う |
| RustBelt（[紹介記事](https://blog.acolyer.org/2018/01/18/rustbelt-securing-the-foundations-of-the-rust-programming-language/)） | 型と型付け判定に分離論理で意味を与え、unsafe を使うライブラリをその意味に対して検証した | 「unsafe の契約とは、署名の意味 ⟦σ⟧ を満たすこと」という構えが同じ。こちらは共有参照も lifetime も並行性もなく、はるかに小さい |
| [Low-Level Liquid Types](https://goto.ucsd.edu/~rjhala/papers/low_level_liquid_types.html)（Rondon, Kawaguchi, Jhala, POPL 2010） | C に対する範囲付きの型で、ポインタ算術とヒープ上の不変条件を扱い、注釈を推論する | 論理式で値を絞る点が同じ。こちらは推論せず、ループの注釈を書かせる |
| [Islaris](https://pub.ista.ac.at/~msammler/paper/islaris.pdf)（Sammler ほか, PLDI 2022） | Armv8-A と RISC-V の機械語を、Sail の ISA モデルの上で分離論理により検証する | 手書き証明の側の比較対象。e5r の機械意味論は独自に書いたもの |
| [FunTAL](https://arxiv.org/abs/1711.03871v1)（Patterson ほか, PLDI 2017） | 関数型言語と型付きアセンブリの安全な混在を形式化した | 異なる規律のコードを境界でつなぐ点が近い。こちらの境界は「検査されたアセンブリ」と「検査されないアセンブリ」の間 |

アセンブリの層で safe と unsafe を明示的に分け、unsafe 側を契約でつなぐ既存の体系は、今回の検索（7 件）では見つけていない。調べた範囲が狭いので、「ない」とは言えない。

読むべきなのにまだ読んでいないもの: RefinedC、CN、eBPF 検証器の設計、[Ownership Types for Verification of Programs with Pointer Arithmetic](https://arxiv.org/pdf/2312.06455)（所有権と範囲付きの型をポインタ算術に広げたもので、条件がこの設計に最も近い可能性がある）。

## この設計が間違いだと分かる条件

次の五つのどれかが起きたら、v0 の設計を見直す。しきい値は決めていない。試す関数の一覧は、結果を見る前に固定しておく必要がある。

1. **表現力が足りない。** リポジトリに既にある関数（`sum`、`cobs_decode`、`write_all`、musl の `mem*` と `str*`）に署名と注釈を付けたとき、大半が unsafe に落ちる。
2. **注釈が書けない。** LLM がループの注釈を安定して書けない。または、検査機の失敗メッセージから直せない。
3. **検査が遅い。** 一関数の検査が対話的に使えない長さになる。新しい変数と 2^64 の係数がソルバを遅くする可能性がある。
4. **健全性の穴が局所的に直せない。** 点検で行き詰まりが見つかり、原因が個々の規則ではなく、法 2^64 で型を定義するという土台にある。
5. **契約が型の言語で書けない。** unsafe 関数の前提がメモリの中身に依存すると、署名に書けない。

5 は既に一つ帰結が見えている。長さなしの `strlen` の前提「範囲内に NUL がある」は v0 の署名で表せない。そういう関数を safe から呼べるようにすると、書かれていない前提が残り、安全性の主張が崩れる。したがって safe 側の文字列は「ポインタと長さ」で持ち、長さの上限を取る `strnlen` の形だけが safe になる。C の慣習とのこのずれが許容できるかは、早めに確かめたい。

## 決定の記録

未決だった十項目は、11/23 にすべて決まった。11 は 11/23 に後から加わった（P1、ユーザーの決定）。1、4、10 は個別に判断し、残りは提案どおりとした。9 と 10 は信頼対象の意味論を変える決定で、e5r 側の変更はまだ行っていない。

| # | 決めること | 決定 | 理由と代償 |
| --- | --- | --- | --- |
| 1 | 部分正当性と全正当性のどちらを既定にするか | 全を既定にして `decreases` を必須にする。止まらない関数だけ `partial` と明示する | 現行の `Exec` と `VerifiedImg` にそのままつながり、手書き証明が検査済みの関数を呼べる。部分だけにすると、新しい判定とその呼出し規則を Lean に足す必要がある。代償は注釈が一句増えることと、`partial` な関数を呼ぶ手書き証明が当面書けないこと |
| 2 | 前向きの合流点の扱い | 一致しないものを捨てる粗い合流にし、足りない所に注釈を置く | 検査機の挙動が予測しやすく、失敗が局所的になる。別案は分岐条件を付けた選言で正確に合流するもので、注釈は減るがソルバへの負荷と記録が大きくなる |
| 3 | unsafe の単位 | 関数だけで始める | 規則が少ない。代償は小さな unsafe 操作に呼出しの費用がかかること |
| 4 | 機械モデルの外のコードを呼ぶことを認めるか | 認める。ただし台帳で「外部」という別の状態にして、仮定と区別する | 認めないと、既存のバイナリをそのまま組み合わせるという要件を満たせない。認めると、証明できない信頼対象が増える |
| 5 | 一次算術のソルバ | Rust の検査機は既存の SMT ソルバを使い、問い合わせを記録する | 問題は小さく、当面は信頼する前提なので自作する理由が薄い。Lean 側で `omega` が 2^64 の係数を含む問い合わせを通せるかは未確認 |
| 6 | 注釈の構文と置き場所 | アセンブリ中のディレクティブとして命令の隣に書き、アセンブラが `.nocompiler.struct` に落とす | 命令と注釈がずれにくい。強い根拠はなく、検査機を書く段階で見直してよい |
| 7 | `Heap` トークンを暗黙に全関数へ通すか | 明示する（`borrow Heap`） | 割当てをする関数が署名で分かる。暗黙化は後から糖衣として足せる |
| 8 | `stack` を添字式にして再帰を許すか | v0 は定数だけ、再帰なし | 添字式にすれば深さが引数で抑えられる再帰は書けるが、要る実例が出てからでよい |
| 9 | 外部の関数を呼ぶ一歩を Step にどう入れるか | 環境モデルに「入口の番地から署名へ」の表を持たせ、pc がその番地にあるとき、署名の関係に従って一歩で戻り先へ進める。ecall と同じ形にする | 信頼対象の意味論と trust.md を変えることになる。外部コードが触れる範囲と戻り方を、署名どおりだと信じることになる |
| 10 | 権限の判定と、give で返る能力の食い違いをどう埋めるか | e5r の権限の判定を「領域の一つに収まる」から「アクセスする全バイトが許されている」に変える | 今の判定だと、隣り合う二つの領域にまたがる能力が返ってきたとき、型の検査を通るアクセスが関数ごとの権限のもとで行き詰まる。別案は権限を作るときに隣り合う領域をつなぐこと。案は信頼対象の意味論を変える |
| 11 | ループの形（S2）を番地の順で決めるか | 決めない。戻りの辺は支配関係で定め、ループは自然ループ、検査は記録が与える順序 τ で行う（2026-11-23 P1 adopted (user)） | 番地の順では clang のブロック配置でループが区間にならず、musl の試行で 29 ファイル中 8 が構造だけで落ちた。代償は記録に τ が増えること。停止の証明は番地を τ に読み替えるだけで変わらない |
| 12 | `heap` の印に意味を与えるか | 与える。`Heap` トークンの不変条件が生きている割当て単位の集まりを公開し、`heap` の能力の範囲はその一つとする。出口の条件に「Pool とスタックに掛からない単位は残る」を足す（2026-11-23 adopted (user)） | 意味がないと、unsafe なアロケータの契約（malloc は新しい単位を渡し、free は生きている単位の全体を受け取る）が偽の前提になる。代償は署名の意味が少し増えることと、呼出しの規則に条件が二つ増えること（自分の借りた能力を take に渡さない、呼出しの時点で借りた能力を手放していない） |

このノートが扱っていないもの: 検査機の実装計画、既存の `next` ブランチ（LPS の移植、musl の証明）との関係、v1 仕様案の R6 をどこまで残すか。
